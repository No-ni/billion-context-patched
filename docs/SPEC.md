# bili-context-patch 独立修改与行为规范

状态：已确认需求；以 0.5.4 为首个核对基线。本文是独立修改的唯一权威清单，规定必须保留的行为；每次更新、修复、合并、升级、重建、安装与发布前须完整阅读。不得另建重复清单或依赖聊天记忆。

## 2. 缓存钥匙：默认开启（B11）

这是用户明确要求的项目默认，适用于全新安装、已有安装升级和从上游重建。与 B6 的 fork 选钥匙规则分别核对。

### PCK-01：默认值及配置优先级

`promptCache.routing` 默认必须为 `enabled`。运行时先取 `ACP_PROMPT_CACHE_ROUTING`；仅当它未定义或为 null 时取配置文件的 `promptCache.routing`，再解析取值。

解析器必须原样保留 `enabled`、`auto`、`disabled`。选中的值缺失、为 null、为空字符串或为不认识的值时，回落 `enabled`。不把空字符串当作“未提供环境变量”。

| 环境变量 | 文件配置 | 生效值 |
| --- | --- | --- |
| 未设置 | 未设置 / null / 无效值 | enabled |
| 未设置 | enabled / auto / disabled | 保留文件值 |
| enabled / auto / disabled | 任意 | 保留环境变量值 |
| 空字符串 / 无效值 | disabled | enabled（先选择环境变量，再解析） |

### PCK-02：尊重显式选择及上游兼容逻辑

`disabled` 必须关闭 bili 自行注入钥匙；`auto` 保留上游按请求路径和目标判断的规则；`enabled` 启用支持路径上的注入。默认开启不表示每一条请求无条件写入字段：客户端自带钥匙、请求身份、支持路径和上游拒绝探测仍由现有兼容逻辑处理。

安装、重装或升级不得为了落实默认值，将用户显式的 disabled/auto/enabled 改写为 enabled，也不得删除同一配置中的其他字段。

### PCK-03：设置页与运行时一致

文件未配置 routing 时，设置页缺省选中 enabled；显式三档设置显示原值。中英文说明必须把“当前默认”标在开启项，关闭项不得再标为默认。

设置页读取的是配置草稿，不代表环境变量覆盖后的最终状态；未知的显式字符串仍可显示为自定义值，不要求自动改写文件。

### PCK-04：可重复应用

默认值和设置页变更必须保存在 `scripts/patch-bili-build.mjs` 的 B11 中，发布的 vendor 构建也必须包含它们。不能只修改本机配置或手改构建产物。

首次应用必须完成迁移；重复应用必须保持文件字节不变；上游目标实现无法识别或锚点不唯一时必须失败，不能静默遗漏。

### PCK-05：验收证据

| 条款 | 当前验收方式 | 覆盖边界 |
| --- | --- | --- |
| PCK-01、PCK-02 | `check-views.mjs` 的 `cache-key routing defaults to enabled and preserves explicit choices` | 提取发布构建的解析与生效函数；环境变量/文件组合表还需核对真实配置加载逻辑；不代表真实网关缓存命中 |
| PCK-02 | `check-wrapper.mjs` 的安装与重装检查 | 自动覆盖禁用状态及渠道配置保留；routing 字段保留需审阅安装差异 |
| PCK-03 | `check-views.mjs` 的 `settings show enabled by default and preserve explicit routing` | 检查构建中的选项计算及中英文默认文案；不替代浏览器交互测试 |
| PCK-04 | 在临时副本从上一发布构建应用补丁，与最终构建比较；再次应用比较文件哈希 | 发布时记录实际结果；不能只看 already patched 输出 |

安装检查必须对最终候选构建运行视图检查与压缩检查，不得绕过失败后发布。

## 3. bili 代理的定制行为

以下编号与维护清单、补丁脚本一致。条款中的条件是功能的一部分，不能在迁移时只保留成功路径、丢掉拒绝条件。B11 对应第 2 节全部 PCK 条款。

B12–B16 的完整行为见第 8 节；B17 对应 W7 的图像卡。B19–B21 只决定失败怎么表现（不自行熔断、不在 shell 上加常驻横幅、把失败原因翻成中文），不改变压缩与传输行为。编号不因实现位置改变。

### B1：出站请求压缩与回执

必须支持折叠后请求体的 off/gzip/br 传输，消费 `x-accel-compress`、`x-accel-rid` 指令并记录压缩回执。只有明确的 `gzip`、`br` 或 `on` 指令才允许压缩；指令缺失、空值或未知值默认 `off`，不能继承全局上游编码配置。显式 `on` 才使用全局算法（未设置时为 gzip）。仅在 POST、目标包含 `/chat/completions`、`/v1/messages` 或 `/responses`、请求体至少 1024 字节且压缩结果小于原文 95% 时应用压缩，已有 content-encoding 时不再次压缩；重复调用保留已有决定。压缩后删除旧 content-length，由发送层计算正确长度。

回执环最多 300 条，保留 encode-stats 查询能力。验收：`smoke.mjs` 验证三路真实本地传输、长度及重复调用；回执接口需真实代理核对。开关与实现细节见维护清单及 PATCHES 第 1–4、10 节。

发送层独立持有请求头副本；同一个已编码 Buffer 的重放不得二次压缩。重建新明文时只清除本补丁为旧正文添加的 encoding/length，继承已消费的压缩指令和回执标识；用户自带的预编码正文及 encoding 保持原有语义。变换、签名与回执须使用本次实际发送的正文和请求头。

### B2：插件道快照渲染

DSH 插件道必须能够使用服务端快照渲染，避免每轮整份重推历史。必须继续受插件道快照标记及上游 snapshot live/shadow 开关控制；允许使用不等于无条件开启。关闭时按原有路径处理。

验收：真实 DSH 中分别验证标记开关与 live/shadow 组合，检查实际出站是否按预期变化。当前自动检查不覆盖开关集成，不能以标记文本存在代替验收。

### B3：fork 首轮借用父记录

fork 尚无自己的统一消息行时，可借父会话记录渲染。子会话已有记录时必须使用自身记录，不能永久跟随父会话；父记录不可用时保留原有降级路径。

验收：真实 fork 的首轮及保存后续轮分别核对记录来源；当前需人工集成验证。

### B4：fork 首次复用父画面

仅在插件道、父 pin 可用且 B10 校验通过时，fork 首次成功可复用父画面并追加尾部。追加最多 8 条且首条不能是 tool；成功后登记子 pin，子会话后续不能再次套用该首次复用。pin 表最多 8 条，仅驻留内存。

验收：`check-views.mjs` 检查前缀编辑拒绝、子 pin 登记、只成功一次及表上限；与 B2/B3 联动还需真实 fork 验证。

### B5：诊断请求体落盘

请求体落盘默认关闭，只有诊断标记文件存在时才开启。关闭时不因普通请求自动输出请求正文文件。

验收：人工验证无标记不写、有标记写入、撤销后停止写入；当前自动检查不覆盖写盘行为。

### B6：fork 缓存钥匙血缘

需要 bili 自行盖钥匙时，fork 沿进程内血缘链选择父会话实际使用的 key，多层 fork 也应继承同一已记录血缘。不得把“父会话 ID”一律视为“父会话实际使用的 key”。记录最多 512 条，重启清空；默认是否开启按 B11 单独验收。

验收：`check-views.mjs` 检查父子孙继承和记录上限；实际网关是否接受、是否命中缓存需真实请求验证。

### B7：fork 历史时间戳继承

只复制 fork 继承前缀中父会话已有的消息时间戳；新消息使用子会话自身时间。子表必须是独立副本，后续改动不能反向修改父表。

继承范围以实际前缀为证，父引用空间中预留但未继承的消息首次在子会话出现时使用子时间。已显示的子时间在重新转换裸消息、内核克隆和保存后重启时保持可见；该证明只覆盖实际首次盖戳的消息。关闭时间显示时先出现的历史、模糊恢复或无法证明的旧时间不因后续开关而伪造时间。

验收：`check-views.mjs` 检查复制范围、运行编号及副本独立性；真实渲染标签还需人工核对。

### B8：存储降级时复用本会话画面

仅在插件道、本会话有 pin、B10 校验通过且尾部合格时，才能使用旧画面追加新消息。历史缩短、前缀变化、摘要失效、追加超过 8 条或追加首条为 tool 时拒绝复用；pin 缺失时不伪造旧画面。

成功复用后登记本次完整的已验证前缀和画面；下一轮的 8 条追加限制相对最近一次成功的 pin 计算。不得因多轮合格的小幅追加累计超过 8 条就丢失已有证明，也不得放宽单轮上限。

验收：`check-views.mjs` 覆盖不变前缀、编辑历史、长文本后半段变化、失效摘要、不合格尾部及连续多轮推进后的完整前缀/摘要校验。重启首轮没有 pin，允许按原有流程降级或拒绝，不能承诺所有存储故障仍可发请求。

### B9：最新块暂时缺行

仅当零消息行的块是最后一个 active 块，且前面至少有一个块已锚住时，才允许这一轮跳过该块；并必须通过 B10 的原文覆盖校验。更老块缺行或只有一个缺行块时，继续拒绝该快照。

验收：`check-views.mjs` 分别覆盖最新块、老块、单块缺失及部分消息缺失；不能只验“最新块跳过成功”。

### B10：消息完整性与画面有效性

旧画面复用必须校验完整客户端历史前缀的 SHA-256，不能退回只检查末条或截断文本；引用的每个摘要块必须仍 active。跳过块的每一条 effectiveMessageId 必须位于最终实际追加的原文尾部，普通和 WS/增量路径遵守同样约束。复用成功须补写 snapshotRenderTailStart。

还须校验影响该前缀的摘要状态和布局，包括 retire/restore、rewrite、展开、层级及覆盖关系；相同 blockId 或 active=true 不足以证明旧布局仍有效。无关新尾部变化不使已经证明的前缀失效。

拼接使用的内容签名须区分工具调用身份；不同 toolCallId 的相同输出不能互相充当锚点。普通快照、WS probe 的产生与校验及 shadow 比较使用一致的签名，不以降低最小 seam 长度绕过证明。

验收：`check-views.mjs` 提取实际签名，覆盖早期编辑、长文本编辑、失效摘要、拼接点前遗漏、部分覆盖、索引落后时的连续相同工具结果及两种请求路径。无法证明完整性时走原有降级/拒绝流程，不得返回成功但静默遗漏消息。存储事务一致性尚未改造，不把此规范当作已完成存储事务重构的声明。

### B18：压缩增长阈值默认 80k

未显式配置 `compress.nudgeGrowthTokens` 时，内核 floor/cap、Web UI 快速配置默认值及中英文提示必须为 80000；显式值保持原值。默认值须纳入重打脚本，不能只写在本机配置里。

中断回合的增长提醒只接受真实上游 `usage` 作为新基准。用于窗口预检的估算 token 数不能消耗中断回合记录、移动提醒基准或清除已显示的提醒状态。

验收：`check-views.mjs` 检查发布构建的内核默认、页面常量与提示文案，并覆盖估算值不改变提醒状态、真实 usage 正常处理及四个调用点都传递来源；`check-image-card.mjs` 同时确认页面脚本可解析。需求来源见第 9 节。

### B19：不自行熔断，失败交给 DSH 重试

代理不得按上游主机累计失败次数、提前失败，也不得返回 503 或 retry-after；连接类失败按普通失败返回（请求体过大仍为 413），由 DSH 自己的退避与重试上限处理。失败分类、告警记录与日志保留，但只进 `/__bili/diagnostics`，不在模型可见处外显。

验收：`check-upstream-ux.mjs` 断言发布构建里没有 `CIRCUIT_OPEN_AFTER`、`circuitProbeCooldownMs`、`upstreamCircuitBlockReason`、`getUpstreamHealthReport`、`/__bili/upstreams` 与 `circuit open` 文案，并有 `__biliFailureTextZh`；实际重试次数与退避需真实网关验证。

### B20：shell 上不显示上游状态横幅

客户端不得轮询上游健康、也不得往 shell 覆盖层注入横幅；上游状态只保留在诊断接口里，不新增需要用户手动关闭的常驻 UI。连接失败时页面提示使用读者能看懂的中文，诊断原文放在可复制的详情里。

验收：`check-upstream-ux.mjs` 断言合并后的 `lib/client.js` 没有 `bili-upstreams`、`upstreams_down_one`、`upstreams_down_many`、`upstream_retry_hint`、`parseUpstreamHealth`、`upstreamBanner`、`UPSTREAM_POLL_MS`，并含「连接 bili 失败」；真实页面是否还有残留横幅需人工确认。

### B21：失败文案用中文短句，诊断留在详情

模型请求失败时，错误字段必须是中文短句加处置说明（重试由 DSH 自动进行），不得把 `acp-proxy failure: ...`、`circuit open` 等内部措辞送进对话窗；详细英文诊断只放在 `detail`、`upstreamFailure` 与日志里。请求体过大保留 413 语义，其余统一 502，不再发 retry-after。`[ACP]` 吸收标记里的 `FAILED` 字样是判定依赖，不得改写。

断流的传输诊断沿用主线的本地日志边界，不附在 SSE 的 `meta` 中；仍保留中文可见错误与合法终止事件。工具结果失败沿用主线只判结果首行，摘要正文引用 `FAILED` 不应误报失败。

验收：`check-upstream-ux.mjs` 提取 `__biliFailureTextZh` 并断言连接超时、拒绝连接、DNS/TLS、代理重置、普通失败与请求体过大六类的中文输出。`check-preflight.mjs` 执行预检 HTTP、四种协议的已提交流错误、本地解码繁忙、实际 reader/decoder/ingest 大小限制、辅助请求窗口 guard、完整 WS 历史重建和本地传输错误，以及模型隧道 DNS 拒绝的响应分支，核对中文、detail/upstreamFailure、retryable、413/502 和没有本地 retry-after。原有协议、身份及策略拒绝的 400/403/409 契约和上游真实限流的转发语义继续保留。

### B22：快照降级后的有界恢复

已启用 live 快照渲染（插件道还需其标记允许）、会话有 active 压缩块，但本轮没有得到合格快照或安全旧画面时，共用预检入口须先等待本会话已排队的保存，最多一秒。保存成功后用现有准备流程重新渲染最多一次，再重新核算窗口和压缩需求；重做不重复计入请求次数。不得清空块、修改引用、绕过 B9/B10 或直接放行已确认超窗的请求。

保存失败或超时不循环等待；客户端断开须结束本轮恢复，取消本轮定时器和关闭监听。重做异常保留原有错误处理。关闭快照、shadow-only、没有 active 块、透传或已有合格画面时不触发恢复。

只对当前准备流程实际发生的暂时读失败保护状态，不能用上一请求遗留的降级原因作证。恢复前不得把重新出现的原始历史误当新实例去重编号、停用 live 块、归档引用或删除原文；该次暂缓保留正常的快照、消息索引和保存排队，成功重做才执行通常的内核与后处理。真正的历史编辑、重置和显式 legacy 模式保持原有处理。

持续缺行、存储暂不可用等已识别的暂时降级，在没有确定性过大、不可缩减图片/协议开销或终止性上游错误时，可标记为可重试，交给 DSH 决定退避和上限；不能只因 seam 太短或覆盖校验失败就无条件重试，也不能用可重试代替完整性证明。

预检内核复用已有块后判定可装入窗口、但准备好的出站视图仍超窗时，即使没有新压缩范围，也须重建实际出站并重新核算。内核的 fit 不代替出站检查；重建后仍不合格时保留原有拒绝与大小保护。重建异常或提前失败也须恢复并持久化正确的请求次数。

验收：`check-preflight.mjs` 用发布构建的真实渲染与预检函数串起首次缺行、保存后恢复、持续缺行与零压缩进展；实际内层压缩函数覆盖零新增范围的已有块 fit、外层四协议重建、重建仍降级及异常计数。二次校正 probe 在成功、提前拒绝、异常和断开后均验证实际保存队列中的请求计数；匿名零新增范围重建按重建后的图片预算判断。同时覆盖不合格 seam、跳过块覆盖失败、413、上游鉴权失败、开关、保存失败/超时和断开。模拟存储和摘要服务不代表真实 DSH 冷加载、模型切换或网关集成已验证。

### B23：每条压缩提醒只允许一次成功的模型折叠

一次实际注入的 compression nudge 对应一个独立 generation。模型工具调用只有在开始时仍有该提醒的有效 credit 才归属该 generation。该提醒下第一次成功创建一个或多个压缩块的模型工具调用即完成并消费该 generation；partial 结果只要已创建至少一个块也算完成。后续同一 generation 的模型工具 `compress` 调用必须拒绝，不能继续折叠并再次改写请求前缀；消费标记保留到新提醒注入。若调用没有创建任何块或异常结束，可在同一提醒下重试；同一 generation 已有压缩调用进行中时，并发调用必须拒绝。过期且未消费的提醒不能认领之后的无提醒折叠。新注入的提醒开启新 generation；旧调用结束时不得消费新提醒的机会或清除新提醒的并发锁。

此限制只包装模型显式调用的 `compress` 工具，不拦截窗口预检等自动压缩路径。一次成功调用仍可按请求折叠多个独立范围。

验收：`check-e2e-mock.mjs` 通过真实 T1 注入验证零块失败可重试、partial 创建块后跨轮重复拒绝、异常后释放锁并可重试、同一提醒并发只有一个调用创建块、新提醒恢复一次机会，以及过期未消费提醒不占用之后的独立折叠；`check-preflight.mjs` 确认自动预检压缩不受模型工具 gate 限制。必须在最终构建上运行，单看补丁锚点或函数文本不算通过。

### B24：流写入轨迹（诊断）

每个代理请求在响应侧各留一行 `[stream-trace]`：`end()` 被调用时记耗时、写入次数与字节数；`finish` 记响应真正写完；`close` 记 `ended`（是否既调用了 `end()` 又 `writableFinished`）、写入次数、字节数与距最后一次写入的空闲毫秒。正常结束按 `debug` 记录，响应未结束就关闭按 `warn` 记录，一次断流因此自己留下证据，而不是只剩 `client disconnected mid-stream`。

此轨迹只读响应对象、只写日志：不改写任何字节、不新增计时器、不改变重试、超时或错误语义；关闭 debug 后异常仍以 `warn` 输出。与 B5 的请求体落盘相同，属诊断输出，不构成对外行为。

## 5. 安装与运维的定制行为

### I1：自包含来源与基线一致

安装优先使用仓库自带 vendor，不能被 profile 的旧副本意外替换；显式外部 bili 来源必须是兼容的补丁构建。保留 build/out/profile 入口，bili 的 manifest、build-info、agent、client、层与 dist 必须属于选定的同一基线。嵌套 vendor 清单不能代替根包依赖安装；运行期使用的 YAML 与账本 schema 解析器必须随包携带或由安装流程确实安装，不能依赖曾经装过原版插件。

未配置存储模式或指定 `sqlite` 时，沿用选定主线的纯 SQLite 默认，不写会话 JSON envelope；显式 `full` 在未选择 writer 时仍双写，显式 `storage.jsonWriter` / `BILI_STORAGE_JSON_WRITER` 优先。legacy/shadow 的既定来源与回退保持。不得借升级改写用户配置或删除已有副本。WAL 文件头检测只读 100 字节，正确识别读写版本均为 2，失败与短文件回退原有判定流程并关闭文件句柄。

写入统一存储侧车的消息 JSON 嵌套深度最多为 512 层，按最终 JSON 结构检测，以避免 Node 版本差异导致递归抽样校验在写入成功后溢栈。超过上限时应在 `plan-ingest` 阶段以消息 ID 记录失败；不得中断 legacy 保存或模型响应，后续保存继续重试。

验收：安装检查来源与必要文件；人工比较基线和完整来源提交。当前没有自动证明整份二进制可复现的检查。

### I2：候选检查后替换

必须先在临时副本打补丁并完成视图与压缩检查，通过后才替换正式 dist；工厂先解析。失败不能覆盖正式 dist，退出时清理任务临时文件。这一要求不表示整个多文件安装已具备事务原子性。

验收：`check-wrapper.mjs` 验证坏候选不覆盖正式 dist；正常安装必须执行候选检查，不用 skip-smoke 绕过发布失败。

### I3：安装合并与配置保留

将 dependencies/bundles 合并为包装包，保留其他插件；按正确寻址迁移旧配置及旧 !!js 跟随行。包装包已有字段优先，旧加速器配置只补缺失字段；已有 disabled 和渠道选择保持原值，不能因重装重新启用或删除配置。自定义表达式不当作旧跟随行删除；YAML 的别名、合并键、标签、注释及无关数据须保持语义。备份仅轮换本包生成的最近 3 份。

插件管理器安装不执行安装脚本；包装包首次启用时完成等价合并——从 `dsh.profile.bundles` 移除两个上游、保留 `dependencies`，迁移旧设置并协调宿主重载。写入必须使用宿主文件锁及原子替换，不能丢失并发安装的无关字段；重载失败需重试，不能只改磁盘后宣称成功。

验收：`check-wrapper.mjs` 检查重复安装、分行禁用状态、渠道选择、YAML 迁移和无关插件；`check-runtime.mjs` 检查官方文件锁、并发字段、回滚、备份轮换与重载失败重试。完整管理器安装仍需真实 DSH 验证。

### I4：指定中转渠道压缩默认值

安装时仅对主机名匹配 `www.didudidu.asia` 或 `154.219.111.56` 的渠道逐字段补缺失的 `enabled: true` 与 `encoding: auto`（优先 br）；已有值不覆盖，显式全局 gzip 的有效选择也须保留。按主机匹配，不依赖渠道名称；其他域名不自动套用该规则。

插件管理器安装由包装包首次启用补齐同样的缺失键，并等待服务就绪、跟踪稍后出现的渠道。缺失与否须依据用户原始配置，不能把 schema 生成的 false 当作用户关闭；已有 false/gzip/null/表达式均不覆盖。并发写入冲突时重新读取最新配置再计算默认值。

验收：`check-wrapper.mjs` 覆盖两个主机、非匹配主机、改名、缺失/显式值、表达式与全局 gzip；`check-runtime.mjs` 用实际 SettingsForms 检查服务迟到、schema 默认、并发选择保留、持久化与活访问器。真实请求是否使用 br 需运行回执验证。

### I5：可靠重启与任务收尾

重启发现实际代理端口，只有新的有效 instanceId 才算替换成功；旧实例仍在响应不算重启完成。探针连接及时关闭。备用启动优先使用包装包内 vendor，保留可获得的宿主看护、通道及模型窗口信息。

只终止本任务创建且不再需要的失败启动进程；成功保留的服务说明用途、PID、端口和停止方式。所有执行会话取得最终状态，临时资源收尾，用户原有进程不受无关操作影响。

验收：`check-restart.mjs` 覆盖动态端口及实例替换；备用启动、宿主看护、竞争启动清理和实际停机需真实环境验证。

- **IMG-12 宿主退役占位还原（缓存前缀）**：DSH 在请求组装阶段把超出图片预算的旧图替换成占位文本（`[image omitted to fit request image limits; …]`）。代理在出站 body 发出前，用同一会话此前实际发出过的「说明文本 + 图片」两段原样换回占位，使被还原的那部分与退役前逐字节一致，提供方前缀缓存继续命中。缓存按会话保存插件亲眼见过的出站字节，上限 96 张、64 MiB、64 个会话，并另设 256 MiB 的全局上限（超限淘汰最久未使用的会话）；只处理 `image omitted to fit request image limits;` 变体，text-only 等其他占位不动；解析不到同会话字节时保留占位并记 debug，解析出错只 warn。宿主可能把整条消息的文本块合并成一个字符串再退役图片（OpenAI Chat 路径），此时按占位把字符串切开重建 text+handle+image 数组；只要求 sha256 token 与“去掉占位、去掉 accelerator 的 `<acp …>` 引用后”的文本一致，重建时保留当前请求的文本和引用，只把 handle 与 image 放回。开关 `imageRestoreHostOffload` 默认开启，环境变量 `BILI_IMAGE_RESTORE` 可覆盖；关闭时占位原样发出。还原只决定线上字节，不承诺两套账一致——图片不计入 token，由 IMG-13 或上游拒绝兜底。
- **IMG-13 上游上传超限兜底**：上游以 413 拒绝且报错文本指向上传或请求体大小（`upload limit`、`upload size`、`payload too large`、`entity too large`、中文“请求体过大/上传大小超限”等），且不是图片数量墙时，代理在同一请求内强制一次有界压缩并按同一上游重发：目标窗口取当前请求体估算、`stats.lastInputTokens` 与模型窗口的最小值，第一轮乘 0.6、第二轮乘 0.35；成功即把折叠后的请求与响应交给调用方并记 `[upload-413]` 日志，失败或不满足条件时把原 413 原样透传。只有报错文本本身是泛化的 `request_too_large` 时，还要求解析不到上下文窗口才按上传超限处理；真实上下文溢出仍由既有分支优先。失败路径必须把 `stats.requests` 恢复到进入本分支前的值，并撤销 `overflowRefold` 对 `pendingForward` 的 body/prepared 替换，不能把未成功的折叠计数成一次请求，也不能让后续记忆保存折叠后的错误视图。不学习、不记录任何上传软上限——渠道之间与同一渠道都会变化。上下文溢出（400/413 带溢出标记）与图片数量墙继续由既有分支处理，IMG-13 不抢占它们的优先级。

五项预算键是 `maxRequestImages`、`imageOffloadCountQuantum`、`requestImageMaxBytes`、`requestImagePixelBudget`、`maxRequestImageBytes`。B16 把这五项连同 IMG-12 的开关 `imageRestoreHostOffload` 一起登记进代理与 native 宿主两个构建的 `KNOWN_TOP_LEVEL_KEYS`（旧构建按原五项形态迁移）；真正未知键的告警与去重保持。B17 只保留预算卡：五项数字之外只增加 IMG-12 的还原开关，IMG-13 没有独立控件。

验收：`scripts/check-image-card.mjs` 覆盖五项默认值、边界、坏配置禁用、保存与恢复默认，并断言折叠/尺寸/约定控件不存在；`scripts/check-image-budget.mjs` 覆盖两条 DeepSeek 路由与 PI provider 路由的持久化、用户显式值、配置变化及卸载恢复，并覆盖同一 `llm-pi-ai` 命名空间下五条 provider 路由逐条写入（模拟每次写入使版本号 +1、过期快照返回 `SETTINGS_CONFLICT`）与未配置 catalog 路由不写入，并覆盖运行中新增 provider 后由 `settings/document-updated` 自动写入、删除 provider 后清理失效备份、备份记录跨重启恢复、settings 服务已销毁时卸载既不抛错也不告警、坏配置回退默认并在修复后恢复、单条路由失败不阻断后续路由、在途写入时销毁仍会恢复并删除备份；`scripts/check-upstream-ux.mjs` 验证五项键不误报、未知键仍告警且去重。已删除的折叠、压缩、约定与回执不再有检查，因为行为本身不存在；真实浏览器保存/重载仍需人工确认。IMG-12/IMG-13 由 `scripts/check-e2e-mock.mjs` 覆盖：同一会话先发原图再发占位，断言重发的消息内容与原图的 text 段、image 段逐字节一致，开关关闭时占位留在线上且没有图片段；再让本地网关对 `/v1/chat/completions` 返回一次上传超限 413，断言同一路径至少发送两次、后一次更小且日志出现 `[upload-413]` 的 folded once 记录；并覆盖宿主把内容合并成字符串时的还原（保留当前 ACP 引用、只放回 handle+image），以及泛化 `request_too_large` 与中文“请求体过大”两种 413。`check-upstream-ux.mjs` 覆盖新键与原五项注册表的迁移，`check-image-card.mjs` 覆盖开关的默认值、保存与恢复默认。
