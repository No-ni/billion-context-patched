状态：已确认需求；以 0.5.4 为首个核对基线。本文是独立修改的唯一权威清单，规定必须保留的行为；每次更新、修复、合并、升级、重建、安装与发布前须完整阅读。不得另建重复清单或依赖聊天记忆。

## 2. 缓存钥匙：默认开启（B11）

这是用户明确要求的项目默认，适用于全新安装、已有安装升级和从上游重建。与 B6 的 fork 选钥匙规则分别核对。

### PCK-01：默认值及配置优先级

`promptCache.routing` 默认必须为 `enabled`。运行时先取 `ACP_PROMPT_CACHE_ROUTING`；仅当它未定义或为 null 时取配置文件的 `promptCache.routing`，再解析取值。

解析器必须原样保留 `enabled`、`auto`、`disabled`。选中的值缺失、为 null、为空字符串或为不认识的值时，回落 `enabled`。不把空字符串当作“未提供环境变量”。

| 环境变量 | 文件配置 | 生效值 |
| --- | --- | --- |
| 未设置 | 未设置 / null / 无效值 | enabled |
| 未设置 | enabled / auto / disabled | 保留文件值 |
| enabled / auto / disabled | 任意 | 保留环境变量值 |
| 空字符串 / 无效值 | disabled | enabled（先选择环境变量，再解析） |

### PCK-02：尊重显式选择及上游兼容逻辑

`disabled` 必须关闭 bili 自行注入钥匙；`auto` 保留上游按请求路径和目标判断的规则；`enabled` 启用支持路径上的注入。默认开启不表示每一条请求无条件写入字段：客户端自带钥匙、请求身份、支持路径和上游拒绝探测仍由现有兼容逻辑处理。

安装、重装或升级不得为了落实默认值，将用户显式的 disabled/auto/enabled 改写为 enabled，也不得删除同一配置中的其他字段。

### PCK-03：设置页与运行时一致

文件未配置 routing 时，设置页缺省选中 enabled；显式三档设置显示原值。中英文说明必须把“当前默认”标在开启项，关闭项不得再标为默认。

设置页读取的是配置草稿，不代表环境变量覆盖后的最终状态；未知的显式字符串仍可显示为自定义值，不要求自动改写文件。

### PCK-04：可重复应用

默认值和设置页变更必须保存在 `scripts/patch-bili-build.mjs` 的 B11 中，发布的 vendor 构建也必须包含它们。不能只修改本机配置或手改构建产物。

首次应用必须完成迁移；重复应用必须保持文件字节不变；上游目标实现无法识别或锚点不唯一时必须失败，不能静默遗漏。

### PCK-05：验收证据

| 条款 | 当前验收方式 | 覆盖边界 |
| --- | --- | --- |
| PCK-01、PCK-02 | `check-views.mjs` 的 `cache-key routing defaults to enabled and preserves explicit choices` | 提取发布构建的解析与生效函数；环境变量/文件组合表还需核对真实配置加载逻辑；不代表真实网关缓存命中 |
| PCK-02 | `check-wrapper.mjs` 的安装与重装检查 | 自动覆盖禁用状态及渠道配置保留；routing 字段保留需审阅安装差异 |
| PCK-03 | `check-views.mjs` 的 `settings show enabled by default and preserve explicit routing` | 检查构建中的选项计算及中英文默认文案；不替代浏览器交互测试 |
| PCK-04 | 在临时副本从上一发布构建应用补丁，与最终构建比较；再次应用比较文件哈希 | 发布时记录实际结果；不能只看 already patched 输出 |

安装检查必须对最终候选构建运行视图检查与压缩检查，不得绕过失败后发布。

## 3. bili 代理的定制行为

以下编号与维护清单、补丁脚本一致。条款中的条件是功能的一部分，不能在迁移时只保留成功路径、丢掉拒绝条件。B11 对应第 2 节全部 PCK 条款。

B12–B16 的完整行为见第 8 节；B17 对应 W7 的图像卡。B19–B21 只决定失败怎么表现（不自行熔断、不在 shell 上加常驻横幅、把失败原因翻成中文），不改变压缩与传输行为。编号不因实现位置改变。

### B1：出站请求压缩与回执

必须支持折叠后请求体的 off/gzip/br 传输，消费 `x-accel-compress`、`x-accel-rid` 指令并记录压缩回执。仅在 POST、目标包含 `/chat/completions`、`/v1/messages` 或 `/responses`、请求体至少 1024 字节且压缩结果小于原文 95% 时应用压缩，已有 content-encoding 时不再次压缩；重复调用保留已有决定。压缩后删除旧 content-length，由发送层计算正确长度。

回执环最多 300 条，保留 encode-stats 查询能力。验收：`smoke.mjs` 验证三路真实本地传输、长度及重复调用；回执接口需真实代理核对。开关与实现细节见维护清单及 PATCHES 第 1–4、10 节。

### B2：插件道快照渲染

DSH 插件道必须能够使用服务端快照渲染，避免每轮整份重推历史。必须继续受插件道快照标记及上游 snapshot live/shadow 开关控制；允许使用不等于无条件开启。关闭时按原有路径处理。

验收：真实 DSH 中分别验证标记开关与 live/shadow 组合，检查实际出站是否按预期变化。当前自动检查不覆盖开关集成，不能以标记文本存在代替验收。

### B3：fork 首轮借用父记录

fork 尚无自己的统一消息行时，可借父会话记录渲染。子会话已有记录时必须使用自身记录，不能永久跟随父会话；父记录不可用时保留原有降级路径。

验收：真实 fork 的首轮及保存后续轮分别核对记录来源；当前需人工集成验证。

### B4：fork 首次复用父画面

仅在插件道、父 pin 可用且 B10 校验通过时，fork 首次成功可复用父画面并追加尾部。追加最多 8 条且首条不能是 tool；成功后登记子 pin，子会话后续不能再次套用该首次复用。pin 表最多 8 条，仅驻留内存。

验收：`check-views.mjs` 检查前缀编辑拒绝、子 pin 登记、只成功一次及表上限；与 B2/B3 联动还需真实 fork 验证。

### B5：诊断请求体落盘

请求体落盘默认关闭，只有诊断标记文件存在时才开启。关闭时不因普通请求自动输出请求正文文件。

验收：人工验证无标记不写、有标记写入、撤销后停止写入；当前自动检查不覆盖写盘行为。

### B6：fork 缓存钥匙血缘

需要 bili 自行盖钥匙时，fork 沿进程内血缘链选择父会话实际使用的 key，多层 fork 也应继承同一已记录血缘。不得把“父会话 ID”一律视为“父会话实际使用的 key”。记录最多 512 条，重启清空；默认是否开启按 B11 单独验收。

验收：`check-views.mjs` 检查父子孙继承和记录上限；实际网关是否接受、是否命中缓存需真实请求验证。

### B7：fork 历史时间戳继承

只复制 fork 继承前缀中父会话已有的消息时间戳；新消息使用子会话自身时间。子表必须是独立副本，后续改动不能反向修改父表。

验收：`check-views.mjs` 检查复制范围、运行编号及副本独立性；真实渲染标签还需人工核对。

### B8：存储降级时复用本会话画面

仅在插件道、本会话有 pin、B10 校验通过且尾部合格时，才能使用旧画面追加新消息。历史缩短、前缀变化、摘要失效、追加超过 8 条或追加首条为 tool 时拒绝复用；pin 缺失时不伪造旧画面。

验收：`check-views.mjs` 覆盖不变前缀、编辑历史、长文本后半段变化、失效摘要和不合格尾部。重启首轮没有 pin，允许按原有流程降级或拒绝，不能承诺所有存储故障仍可发请求。

### B9：最新块暂时缺行

仅当零消息行的块是最后一个 active 块，且前面至少有一个块已锚住时，才允许这一轮跳过该块；并必须通过 B10 的原文覆盖校验。更老块缺行或只有一个缺行块时，继续拒绝该快照。

验收：`check-views.mjs` 分别覆盖最新块、老块、单块缺失及部分消息缺失；不能只验“最新块跳过成功”。

### B10：消息完整性与画面有效性

旧画面复用必须校验完整客户端历史前缀的 SHA-256，不能退回只检查末条或截断文本；引用的每个摘要块必须仍 active。跳过块的每一条 effectiveMessageId 必须位于最终实际追加的原文尾部，普通和 WS/增量路径遵守同样约束。复用成功须补写 snapshotRenderTailStart。

验收：`check-views.mjs` 覆盖早期编辑、长文本编辑、失效摘要、拼接点前遗漏、部分覆盖和两种请求路径。无法证明完整性时走原有降级/拒绝流程，不得返回成功但静默遗漏消息。存储事务一致性尚未改造，不把此规范当作已完成存储事务重构的声明。

### B18：压缩增长阈值默认 80k

未显式配置 `compress.nudgeGrowthTokens` 时，内核 floor/cap、Web UI 快速配置默认值及中英文提示必须为 80000；显式值保持原值。默认值须纳入重打脚本，不能只写在本机配置里。

验收：`check-views.mjs` 检查发布构建的内核默认、页面常量与提示文案；`check-image-card.mjs` 同时确认页面脚本可解析。需求来源见第 9 节。

### B19：不自行熔断，失败交给 DSH 重试

代理不得按上游主机累计失败次数、提前失败，也不得返回 503 或 retry-after；连接类失败按普通失败返回（请求体过大仍为 413），由 DSH 自己的退避与重试上限处理。失败分类、告警记录与日志保留，但只进 `/__bili/diagnostics`，不在模型可见处外显。

验收：`check-upstream-ux.mjs` 断言发布构建里没有 `CIRCUIT_OPEN_AFTER`、`circuitProbeCooldownMs`、`upstreamCircuitBlockReason`、`getUpstreamHealthReport`、`/__bili/upstreams` 与 `circuit open` 文案，并有 `__biliFailureTextZh`；实际重试次数与退避需真实网关验证。

### B20：shell 上不显示上游状态横幅

客户端不得轮询上游健康、也不得往 shell 覆盖层注入横幅；上游状态只保留在诊断接口里，不新增需要用户手动关闭的常驻 UI。连接失败时页面提示使用读者能看懂的中文，诊断原文放在可复制的详情里。

验收：`check-upstream-ux.mjs` 断言合并后的 `lib/client.js` 没有 `bili-upstreams`、`upstreams_down_one`、`upstreams_down_many`、`upstream_retry_hint`、`parseUpstreamHealth`、`upstreamBanner`、`UPSTREAM_POLL_MS`，并含「连接 bili 失败」；真实页面是否还有残留横幅需人工确认。

### B21：失败文案用中文短句，诊断留在详情

模型请求失败时，错误字段必须是中文短句加处置说明（重试由 DSH 自动进行），不得把 `acp-proxy failure: ...`、`circuit open` 等内部措辞送进对话窗；详细英文诊断只放在 `detail`、`upstreamFailure` 与日志里。请求体过大保留 413 语义，其余统一 502，不再发 retry-after。`[ACP]` 吸收标记里的 `FAILED` 字样是判定依赖，不得改写。

验收：`check-upstream-ux.mjs` 提取 `__biliFailureTextZh` 并断言连接超时、拒绝连接、DNS/TLS、代理重置、普通失败与请求体过大六类的中文输出。`check-preflight.mjs` 执行预检 HTTP、四种协议的已提交流错误和本地解码繁忙分支，核对中文、detail、retryable、413/502 和没有本地 retry-after。上游真实限流的转发语义继续保留。

### B22：快照降级后的有界恢复

已启用 live 快照渲染（插件道还需其标记允许）、会话有 active 压缩块，但本轮没有得到合格快照或安全旧画面时，共用预检入口须先等待本会话已排队的保存，最多一秒。保存成功后用现有准备流程重新渲染最多一次，再重新核算窗口和压缩需求；重做不重复计入请求次数。不得清空块、修改引用、绕过 B9/B10 或直接放行已确认超窗的请求。

保存失败或超时不循环等待；客户端断开须结束本轮恢复，取消本轮定时器和关闭监听。重做异常保留原有错误处理。关闭快照、shadow-only、没有 active 块、透传或已有合格画面时不触发恢复。

持续缺行、存储暂不可用等已识别的暂时降级，在没有确定性过大、不可缩减图片/协议开销或终止性上游错误时，可标记为可重试，交给 DSH 决定退避和上限；不能只因 seam 太短或覆盖校验失败就无条件重试，也不能用可重试代替完整性证明。

验收：`check-preflight.mjs` 用发布构建的真实渲染与预检函数串起首次缺行、保存后恢复、持续缺行与零压缩进展；同时覆盖不合格 seam、跳过块覆盖失败、413、上游鉴权失败、开关、保存失败/超时、断开和请求计数。模拟存储和摘要服务不代表真实 DSH 冷加载、模型切换或网关集成已验证。

## 4. 包装包的定制行为

### W1：一张卡承载三项能力

包装包必须承载 bili、compaction gate、accelerator 三个子插件，保留 bili 与加速器各自的设置页。显式导出 Config，传入活配置访问器时不二次解析而丢掉动态配置能力。

验收：真实 DSH 检查单张插件卡、两组设置与设置变更生效；关闭包装包后其子插件随之停用。当前需人工集成验证。

### W2：合并客户端

合并两个上游客户端工厂，注入依赖取并集；加速器设置命名空间、版本路由和提示文案指向包装包。上游封装或唯一重写锚点不兼容时必须报错，不能生成半成品。

验收：构建时解析工厂并检查重写锚点；发布后人工检查两个设置页及包装包版本入口。生成文件须由安装脚本产生。

### W3：组合层保留与去重

组合层只保留包装包的 insert，保留上游 compaction-basic 设置、四个 preset 的闸门注入及两项 DeepSeek retryPolicy。升级时保留上游新增且兼容的字段，不能因整体替换 inject/config 丢失能力。

验收：重建后人工逐项比较选定上游层与最终组合层，并在 DSH 检查 preset 不因缺失闸门服务而卡住。

### W4：重复上游条目与销毁

启动前扫描并在运行期跟踪，抑制同一功能的上游重复条目，避免重复服务和路由。已经开始初始化的原版必须完成初始化并释放资源，才允许包装包子插件挂载；加载顺序不能影响结果。销毁包装包后必须取消排队启动并撤销自己安装的 guard，不能重新挂载已经停用的子插件。

验收：`check-wrapper.mjs` 检查 guard 生命周期与取消启动；`check-runtime.mjs` 用实际 Loader 检查两种顺序、资源去重和销毁后原版可恢复。`check-ledger-runtime.mjs` 检查原版迟到账本先完成再释放，以及内置加速器关闭时等待异步打开、读失败后的资源释放、服务迟到/重载和排队写入；不得关闭不属于被停用插件的账本。真实 DSH 的客户端、插件开关与热重载仍需集成验证。

### W5：补齐 fork 父会话关系

seeded create 必须获得对应 fork 的 parentSession，已有父字段保持原值，普通创建不误补父会话。并发 fork 的上下文相互隔离；销毁时恢复所包装服务。

验收：`check-wrapper.mjs` 检查并发父会话隔离、已有父字段、非 seeded 创建与服务恢复；`check-runtime.mjs` 用实际 Cordis 服务代理检查包装和恢复。真实 fork 的父关系与压缩状态继承需人工核对。

### W6：包装包版本与更新

提供包装包自己的版本查询和更新入口，并发更新共享串行任务。checkout 更新使用 git pull --ff-only 后运行 installer，不能隐式覆盖本地分叉；没有 patchRepo 时提示走插件管理器。成功与失败都应对用户可见。

同版修复使用构建内容标识与创建时间识别较新的发布；重复构建保持标识和时间稳定，较旧远端不提示更新。常规版本规则及本次不升版的用户决定见第 9 节。

验收：`check-wrapper.mjs` 覆盖版本比较、同版修复、旧远端及坏元数据；接口提示、并发触发、实际更新成功/失败和无 patchRepo 的提示仍需集成验证。

### W7：配置页里的图像卡（0.6.4）

## 5. 安装与运维的定制行为

### I1：自包含来源与基线一致

安装优先使用仓库自带 vendor，不能被 profile 的旧副本意外替换；显式外部 bili 来源必须是兼容的补丁构建。保留 build/out/profile 入口，bili 的 manifest、build-info、agent、client、层与 dist 必须属于选定的同一基线。嵌套 vendor 清单不能代替根包依赖安装；运行期使用的 YAML 与账本 schema 解析器必须随包携带或由安装流程确实安装，不能依赖曾经装过原版插件。

验收：安装检查来源与必要文件；人工比较基线和完整来源提交。当前没有自动证明整份二进制可复现的检查。

### I2：候选检查后替换

必须先在临时副本打补丁并完成视图与压缩检查，通过后才替换正式 dist；工厂先解析。失败不能覆盖正式 dist，退出时清理任务临时文件。这一要求不表示整个多文件安装已具备事务原子性。

验收：`check-wrapper.mjs` 验证坏候选不覆盖正式 dist；正常安装必须执行候选检查，不用 skip-smoke 绕过发布失败。

### I3：安装合并与配置保留

将 dependencies/bundles 合并为包装包，保留其他插件；按正确寻址迁移旧配置及旧 !!js 跟随行。包装包已有字段优先，旧加速器配置只补缺失字段；已有 disabled 和渠道选择保持原值，不能因重装重新启用或删除配置。自定义表达式不当作旧跟随行删除；YAML 的别名、合并键、标签、注释及无关数据须保持语义。备份仅轮换本包生成的最近 3 份。

插件管理器安装不执行安装脚本；包装包首次启用时完成等价合并——从 `dsh.profile.bundles` 移除两个上游、保留 `dependencies`，迁移旧设置并协调宿主重载。写入必须使用宿主文件锁及原子替换，不能丢失并发安装的无关字段；重载失败需重试，不能只改磁盘后宣称成功。

验收：`check-wrapper.mjs` 检查重复安装、分行禁用状态、渠道选择、YAML 迁移和无关插件；`check-runtime.mjs` 检查官方文件锁、并发字段、回滚、备份轮换与重载失败重试。完整管理器安装仍需真实 DSH 验证。

### I4：指定中转渠道压缩默认值

安装时仅对主机名匹配 `www.didudidu.asia` 或 `154.219.111.56` 的渠道逐字段补缺失的 `enabled: true` 与 `encoding: auto`（优先 br）；已有值不覆盖，显式全局 gzip 的有效选择也须保留。按主机匹配，不依赖渠道名称；其他域名不自动套用该规则。

插件管理器安装由包装包首次启用补齐同样的缺失键，并等待服务就绪、跟踪稍后出现的渠道。缺失与否须依据用户原始配置，不能把 schema 生成的 false 当作用户关闭；已有 false/gzip/null/表达式均不覆盖。并发写入冲突时重新读取最新配置再计算默认值。

验收：`check-wrapper.mjs` 覆盖两个主机、非匹配主机、改名、缺失/显式值、表达式与全局 gzip；`check-runtime.mjs` 用实际 SettingsForms 检查服务迟到、schema 默认、并发选择保留、持久化与活访问器。真实请求是否使用 br 需运行回执验证。

### I5：可靠重启与任务收尾

重启发现实际代理端口，只有新的有效 instanceId 才算替换成功；旧实例仍在响应不算重启完成。探针连接及时关闭。备用启动优先使用包装包内 vendor，保留可获得的宿主看护、通道及模型窗口信息。

只终止本任务创建且不再需要的失败启动进程；成功保留的服务说明用途、PID、端口和停止方式。所有执行会话取得最终状态，临时资源收尾，用户原有进程不受无关操作影响。

验收：`check-restart.mjs` 覆盖动态端口及实例替换；备用启动、宿主看护、竞争启动清理和实际停机需真实环境验证。

## 8. 图片只发一次（B12–B16）

模型请求是无状态的：每轮把整段对话重新发一遍，图片以 base64 内联，体积约为原文件 ×4/3。一张 280 KB 的整页截图因此会让之后每一轮请求体多出约 370 KB；缓存命中能省 token，省不掉带宽和发送耗时（实测一个排版会话 45 次调用从 83.8 KB 涨到 1.51 MB，图片占 78%）。本节规定必须保留的行为。

- **IMG-01 只在看过的那一次上送**：一张图成功发送一次后，之后任何请求把它替换成一行文字占位说明，含尺寸、引用号、已看过提示，并在 `acp_read_original_image` 工具存在时给出 `acp_read_original_image("<ref>")` 的取回方式。原图必须始终能用该工具按引用取回——这是「丢弃」的兜底，不是可选项。
- **IMG-02 记账必须在发送成功之后**：折叠判定只认 `noteSuccessfulForward` 里落账的图片。上游拒收、超时、连接失败的请求不算看过，下一轮必须仍发原图。
- **IMG-03 当前回合的上传豁免**：用户刚在当前回合上传的图（最后一条普通 user 消息里）默认不折叠，否则用户贴图提问时会立刻看到占位说明。工具返回的截图不豁免。可用 `imageRetentionKeepLastUser=false` 关掉。
- **IMG-04 首次上送按需压缩**：长边超过 `imageRetentionMaxDim`（默认 1200，最小 128）或原始字节超过 100 KB 时才压缩；JPEG(q80) 与 PNG 两路都试，取更小且不超过原图 0.8 倍的一路，否则保持原样。压缩能力只借宿主已有的编码器：macOS 的 `/usr/bin/sips`、Windows PowerShell 的 `System.Drawing`、其它平台 PATH 上的 ImageMagick；一个都不可用、命令缺失、超时或产物不达标时静默跳过，不得影响折叠。透明 PNG 转 JPEG 会合成白底，可接受，因为原图仍可取回。
- **IMG-05 顺序与体积重算**：折叠与压缩必须在体积削减（`shedEgressIfOverBudget`）之前执行，并复用同一个 `outboundCopyRewritten` 标记，让下游按新体积重算请求头。
- **IMG-06 约定注入必须恒定**：系统提示尾部追加一段恒定的图像使用约定（`imagePrompt`，默认开），说明图片有体积与重传成本、能不用图就不用、要看就一次看够、出图够判断即可、看过之后会变成占位说明并提示按 ref 取回。必须恒定：它落在带 `cache_control` 的最后一块 system 文本里，恒定则稳态零成本；按条件注入会整段作废缓存前缀。
- **IMG-07 覆盖范围**：四个协议（anthropic / openai chat / responses / google，含 tool_result、image_url、input_image、inlineData 四种形状）与两种压缩策略（function / hybrid）都要覆盖，不能只在一条线路上生效；从原图工具取回的回执图不得跳过。
- **IMG-08 配置与回滚**：`imageRetention=false` 关闭折叠与压缩、`imageRetentionKeepLastUser=false` 关闭上传豁免、`imageRetentionMaxDim` 调整长边上限、`imagePrompt=false` 关闭约定；环境变量 `BILI_IMAGE_RETENTION` / `BILI_IMAGE_PROMPT` 优先于配置文件，`0/false/off` 视为关闭。新增顶层键必须登记进 `KNOWN_TOP_LEVEL_KEYS`。回滚只改配置，不重打补丁。
- **IMG-09 配置页可改**：四个开关必须在 bili Web UI 的「配置」页里可读可改，读写同一个配置文件；保存沿用页面原有的 `PUT /__bili/config`，不新增接口；改动对下一条请求生效（环境变量除外）。卡片细节见 W7。

验收：`scripts/check-image-retention.mjs` 离线覆盖四协议折叠、记账后才折叠、上传豁免、工具结果图折叠、总开关、三平台后端的顺序与命令行、本机可用后端的真实压缩与约定文本；Windows 的端到端压缩需 Windows 主机，其它平台跳过；不调用真实模型、不依赖网络。上游 jimp 降采样链因依赖未安装而从未生效，不得把「改 `IMAGE_RESCALE_DEFAULT_MAX_DIM`」当作压缩实现。
