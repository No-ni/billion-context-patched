## 2. 结论与原分析的修正

**错误真实存在，而且属于可以复发的快照降级/预检衔接问题；这一次在下一次尝试时恢复，不表示代码已修好。**

已证实的链路：冷加载有压缩块的会话 → 快照渲染返回 `block-unanchored` → 交出原始历史 → 预检估算超窗、没有完成新的压缩 → 本地返回 502，未转发该超窗请求 → 下一次尝试成功渲染已有压缩状态。

原分析里以下判断应收窄：

- `321 covered reasoning core(s) dropped` 不能单独作为“哈希全部失效”的证据。`reconcileFoldCoverage()` 明确将只有 reasoning 缺失、text/tool 完整的情况判为 `reasoningOnlyDrop`，日志写的是 `fold substrate healthy, tolerated`；恢复后的成功请求也持续出现相同日志。本次 `block-unanchored` 日志还先于这条日志发生。
- `block-unanchored` 指某个 active 块在当前 transcript 行中找不到覆盖消息，**不代表十个块全部失效**。渲染器只要遇到不满足 B9 例外的缺行块，就拒绝整份快照。
- “109 分钟前的快照”来自冷加载警告；可以证明恢复的状态较旧，不能由此认定丢失了 109 分钟的对话或已经证明保存故障。
- 日志证明下一次尝试恢复了渲染，不能证明内部进行过某种特定的“锚点重建”，也不能据此承诺重建只需几毫秒。两次请求的本地总耗时分别为 332 ms 与 115 ms。
- 本次失败在本地预检发生。后续请求实际计量约 100k，说明 424k 是降级原始历史的估算，不能把它当作已经送入模型的用量。
- 与 `v0.6.5` 逐字节比较，`maybeSnapshotView()`、`legacyFor()`、`loadTranscriptBase()`、`preflightCompress()` 和 `preflightCompressIfNeeded()` 的实现均未变化，相同类型日志也早于本次升级，因此没有证据支持由 0.6.6 引入；但 0.6.6 宣称的 B19/B21 错误口径确实漏掉了预检分支。

## 5. 已确认的问题与修复边界

### F1（优先处理）：零进展时不重新渲染已有摘要

位置：代理构建中的 `maybeSnapshotView()`、`legacyFor()`、`loadTranscriptBase()`、`preflightCompress()` 和 `preflightCompressIfNeeded()`。

`loadTranscriptBase()` 遇到不能套用 B9 的零行 active 块会返回 `block-unanchored`；`legacyFor()` 在没有可用 pin 时返回客户端原始历史。pin 只存在内存里，冷启动无 pin；换模型改变前缀、历史编辑、超过 8 条尾部或失效摘要等也可能令旧 pin 拒绝复用。这些保护符合 B8–B10，不能为了消除红字直接放宽。

内层预检按 active blocks 的 `effectiveMessageIds` 排除已覆盖消息，即使本轮快照没有成功渲染。因而“原文很大”和“没有新的可压缩范围”可以同时出现；0 ranges 不能简单理解为对话里没有可压缩内容，也不唯一指向锚点问题。

外层预检只在 `result.compressedRanges > 0` 时调用 `runPrepare()`；如果本轮没有生成新压缩块，即便存储此后已经能渲染已有摘要，也不会重新生成请求。这是本次实际函数隔离验证覆盖的衔接缺口，不是对当时具体哪条消息行失配的复原。

修复候选：识别“有 active 摘要但本轮渲染已降级”的状态，在最终拒绝前等待本会话必要的存储工作并有界重渲染一次，再重新计量；仍不能证明覆盖时继续拒绝。必须保留完整前缀校验、摘要有效性和 skipped-block 覆盖证明，并覆盖四协议与 WS/增量路径。不能无条件多跑 `processTurn()`：它会改状态和请求计数；也不能清空压缩块或把全部已覆盖原文强行重新压缩。

### F2：可恢复的渲染失败被标成不可重试

本次返回 `retryable:false`，但约一秒后的下一次尝试已经成功。外层预检从内层压缩结果推导重试性，没有区分临时渲染降级与真正不可缩减的输入。尊重该字段的调用方可能提前放弃。

本机后续尝试已发生，不能据此声称 DSH 一定遵从这个字段或完全停止重试。修复应针对可恢复类别、限制次数；巨型粘贴、图片/系统提示不可缩减、消息数量硬上限等不能统一改成可重试。

### F3：预检的 HTTP 和四协议流错误绕过中文错误处理

`preflight_compress_failed` 有独立 HTTP JSON 返回和 `emitPreflightError()`，都直接取 `outcome.message` / `error.message`，不经过 `buildProxyFailureResponse()` 或 `__biliFailureTextZh()`。

隔离执行实际 HTTP 分支，413、502、503 都保留原始英文；实际执行流错误函数，openai、responses、google、anthropic 四种协议也都输出原始英文。代理请求提前提交响应头后同样存在，不只是初始 JSON 分支。

这是 B21 已登记要求的实现偏差。修复应在公共预检错误对象处统一中文用户提示并保留诊断详情，再接到所有 HTTP/流协议，不能只替换一处报错字符串。

### F4：预检仍有本地 503 与固定 retry-after

外层把摘要请求的上游 429 映射成 503；HTTP 返回分支在 `outcome.status===503` 时设置 `retry-after: 30`。已隔离执行该响应分支确认。它不会在本次 502 上出现，但与 B19/B21 的现有要求不一致。

相邻的请求解码资源繁忙分支还会返回 503、`retry-after: 1`，是独立的本地资源保护入口；`answerLocalThrottleReject()` 对真实上游 429 的本地 hold 也仍存在。这些不等于已删除的连接失败熔断，不能混为一次“circuit 又回来了”。后续处理 B19 的统一错误口径时须分别明确资源背压、上游限流与上下文不可缩减的语义，保留必要保护，不能批量删所有 503/429 字面量。

### F5：三种流协议丢失 retryable 字段

`emitPreflightError()` 先创建带 `retryable` 的错误对象，但只有 openai 流直接发送完整对象；responses、google、anthropic 分别重新构造错误时没有传出该字段。实际运行该函数并传入 `retryable:true`，输出结果如下：

| 协议 | 原始英文仍在 message 中 | 输出保留 retryable |
| --- | --- | --- |
| openai | 是 | 是 |
| responses | 是 | 否 |
| google | 是 | 否 |
| anthropic | 是 | 否 |

协议原生格式不完全相同，不能直接断言给所有原生 error 塞任意字段都兼容。修复须验证对应客户端能接收的扩展/元数据位置，以及统一的用户提示；这次没有验证 DSH 对各协议元数据的消费。

### F6：已有检查不能证明上述分支正确

`check-upstream-ux.mjs` 检查连接失败文案函数和已删除的熔断/横幅标记，没有执行预检 HTTP/流响应，也未检测残留的 `retry-after: 30`。`check-views.mjs` 覆盖旧块缺行拒绝、最新块跳过的覆盖证明与 pin 安全，但没有把“冷加载首轮降级 → 零进展预检 → 存储恢复 → 下一轮成功”接成一次流程。

本次两项既有检查均通过，缺陷仍可由实际函数隔离执行重现。因此不能用“check 全绿”推断预检错误口径已全面符合规范。
